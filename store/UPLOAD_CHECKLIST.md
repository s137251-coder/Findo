## Four bugs this caught

### 1. The release build did not start at all

The first signed release build **crashed on launch**, while the debug build was
fine:

```
FATAL EXCEPTION: main
java.lang.RuntimeException: Unable to get provider androidx.startup.InitializationProvider
Caused by: Failed to create an instance of androidx.work.impl.WorkDatabase
```

WorkManager arrives with the Ads SDK and is started by `androidx.startup`
before any Dart runs. Its Room database is instantiated by name --
`Class.forName(database + "_Impl")` -- which R8 cannot trace, so minification
renamed the generated class away and the app died in `Application.onCreate`.

Enabling `isMinifyEnabled` is what exposed it; Flutter's default template
leaves minification off. The fix was keep rules for Room, WorkManager and
`androidx.startup` rather than turning minification back off. Rebuilt,
reinstalled, and confirmed launching cleanly.

Worth knowing because a debug build would never have shown this, and the app
would have been dead on arrival for every single player.

### 2. Part of every map was untappable

The opaque objective panel is a Flutter overlay above the game canvas, so it
swallows taps before the game sees them -- and the camera bounds pin the map's
bottom edge to the viewport's bottom edge at *every* zoom level, so the bottom
slice of every map sat under the panel permanently. A Findo hidden down there
could not be tapped at all.

The fix gives the camera a `FixedSizeViewport` that stops above the HUD, and
has the HUD measure its own height and report it. Two follow-on defects turned
up while proving it: the height was first measured against `MediaQuery`, whose
height inside the game widget has already had the navigation bar removed from
it, and the corrected value was then dropped because it arrived before the game
finished loading. Both are fixed; the map's bottom edge now lands exactly on
top of the panel.

### 3. A hint could drag the camera off the map

`setBounds` clamps the camera while the player drags, but it does that through
a behaviour on the viewfinder -- and the hint's `MoveToEffect` writes the
viewfinder position straight afterwards. A hint aimed at a Findo near an edge
therefore won, and the map slid away from the viewport leaving black bands
down one side and along the bottom for the rest of the level.

Fixed by clamping the hint's destination to the legal camera range *before*
asking for the move, which does not depend on which of the two runs last.

### 4. The level chevron pointed backwards in Hebrew

The code chose `chevron_left` under RTL and `chevron_right` otherwise. But
Flutter already mirrors those icons in an RTL context, so the manual swap
flipped it a second time and every row in the Hebrew level list pointed back
out of the level it opens. Fixed by naming one icon and letting Flutter mirror
it.

## The honest summary

**The build is upload-ready, and the account is now verified.**

`app-release.aab` at `1.0.0+3` carries **twenty-five levels** and is ready for
the internal testing track: correctly signed, correctly versioned, and every
graphic and text asset Play demands exists in this repo.

Levels 26 to 30 are drawn and built but not in this bundle. Level 26 came back
from the model with its own near-misses labelled in the artwork, and until it
is regenerated the four levels after it stay out of the manifest, because the
unlock chain runs on consecutive indexes. That is a content gap, not a blocker:
twenty-five levels is a complete game to ship.

What stands between you and a **production** release is account work, not
engineering: a Play Console account, a hosted privacy policy URL, and an AdMob
account for real ad ids. None of it touches the code.

One thing to fix before you make any real money: the ad ids. Shipping to
production with Google's test ids means players see ads and you earn nothing
from them, and it is against AdMob policy to leave them in a live app.

One thing to plan around: a **new personal developer account must run a closed
test with at least 12 testers for 14 continuous days** before it may apply for
production access. That clock cannot start until the account is verified and a
build is uploaded, so the account is the first thing to do even though it is
not the first thing on the list below. Check the exact wording in the console,
as Google revises this policy.
